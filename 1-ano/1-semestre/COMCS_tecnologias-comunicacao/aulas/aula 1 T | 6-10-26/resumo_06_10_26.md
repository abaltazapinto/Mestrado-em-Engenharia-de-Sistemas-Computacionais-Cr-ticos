A ideia importante para **sistemas críticos** é diferente da otimização normal de sistemas.

Num sistema genérico podemos querer:

> maximizar a utilização dos recursos.

Num sistema crítico podemos aceitar:

> recursos subutilizados se isso aumentar segurança, previsibilidade ou robustez.

Exemplo dado: ambiente industrial onde uma falha de comunicação pode parar uma máquina/linha durante horas.

### Ideia nuclear

```text
Sistema convencional
→ eficiência / throughput / utilização

Sistema crítico
→ previsibilidade + disponibilidade + robustez
```

O professor usa sistemas industriais precisamente para mostrar que **uma falha de comunicação pode ter um custo muito superior ao custo de deixar capacidade da rede inutilizada**.

# 1.6 Criar fiabilidade por cima de UDP

Se UDP não confirma a entrega, a aplicação pode criar o seu próprio mecanismo.

Exemplo dado na aula:

```text
Client                         Server
   |                              |
   | -------- message ----------> |
   |                              |
   | <---------- ACK ------------ |
   |                              |
```

ACK = **acknowledgement**.

O cliente pode decidir:

> só continuo depois de receber confirmação.

Isto acrescenta fiabilidade, mas cria outro problema.

### E se o ACK nunca chegar?

O cliente pode ficar:

```text
blocked forever
```

Por isso entram:

- timeout;
- non-blocking sockets;
- polling;
- threads/processos;
- `select()`.

As tuas notas já identificavam ACK e sockets não bloqueantes. COMCS-6-10-26

# 1.7 Blocking, polling, timeout e `select()`

### Blocking socket

A aplicação faz algo equivalente a:

```text
receive()
   ↓
espera...
   ↓
espera...
```

até existirem dados.

---

### Non-blocking

Pergunta:

```text
há dados?
```

Se não houver:

```text
return
```

Mas fazer:

```text
há dados?
há dados?
há dados?
há dados?
...
```

continuamente é **polling**.

O professor é bastante explícito: isto pode desperdiçar muito CPU.

---

### Timeout

Melhor opção em muitos casos:

```text
esperar dados
     ↓
até N ms
     ↓
se nada chegar → erro/timeout
```

---

### `select()`

Outro mecanismo mencionado:

```text
socket A ─┐
socket B ─┼─→ select() → qual tem dados?
socket C ─┘
```

Permite esperar eficientemente por atividade em vários sockets.

Este ponto tem forte potencial de aparecer numa aula prática em **C/Linux**.

# 1.17 Sequence numbers

Solução:

```text
Frame 0
Frame 1
Frame 2
Frame 3
...
```

# 1.18 RTT — Round Trip Time

RTT aparece quando o professor analisa o custo de esperar constantemente pelo ACK.

```text
Sender → Receiver → Sender
        <---RTT--->
```

Se fizermos:

```text
send frame
wait ACK
send frame
wait ACK
send frame
wait ACK
```

e o RTT for grande, passamos muito tempo **sem transmitir nada**.

A rede pode ficar muito abaixo da sua capacidade.

# 1.19 Sliding Window Protocol

Esta é praticamente a conclusão técnica da aula.

Em vez de:

```text
send 0
wait
send 1
wait
send 2
wait
```

podemos permitir várias frames “em voo”.

Exemplo, window size = 3:

```text
Sender:

[0][1][2]  3  4  5  6
 └ window ┘
```

Pode enviar:

```text
0
1
2
```

sem esperar individualmente pelo ACK de cada uma.

Quando chegam confirmações:

```text
ACK 0
```

a janela avança:

```text
0 [1][2][3] 4 5 6
```

Daí:

> **sliding window**

A aula termina precisamente nesta mecânica e na relação com **flow control**. COMCS-6-10-26

---

## Porquê?

Há dois problemas simultâneos:

### Performance

Não desperdiçar um RTT inteiro depois de cada frame.

### Flow control

Não enviar mais depressa do que o recetor consegue processar.

```text
Fast sender
    ↓↓↓↓↓↓↓
receiver buffer
    ↓
OVERFLOW
```

Sliding window limita o número de frames pendentes.

# 2. Explain Difficult Parts Simply

## UDP vs TCP

Pensa em:

**UDP = mandar cartas.**

```text
envias
→ não sabes imediatamente se chegou
→ podem perder-se
→ podem chegar fora de ordem
```

**TCP = chamada telefónica com alguém a controlar a conversa.**

```text
estabelece relação
→ controla receção
→ controla ordem
→ controla fluxo
```

---

## ACK + timeout

ACK significa apenas:

> “recebi aquilo.”

Timeout significa:

> “já esperei demasiado; vou assumir que alguma coisa falhou.”

Juntos:

```text
send → wait → ACK?
              ├─ yes → next
              └─ no → retransmit
```

---

## Jitter

Latency:

> quanto demora.

Jitter:

> quanto esse tempo varia.

Exemplo:

```text
10 ms, 10 ms, 10 ms, 10 ms
```

latência existe, jitter baixo.

```text
5 ms, 50 ms, 8 ms, 80 ms
```

jitter elevado.

---

## Sequence number

É simplesmente colocar um número na mensagem.

Como numerar páginas:

```text
1/4
2/4
3/4
4/4
```

Se aparecer:

```text
2/4
```

duas vezes, sabes que uma é repetida.

---

## Sliding window

Imagina uma fábrica com capacidade para **5 caixas em processamento**.

Não precisas esperar pela caixa 1 terminar antes de enviar a 2.

Podes enviar:

```text
1 2 3 4 5
```

Quando a 1 sai:

```text
2 3 4 5 6
```

A janela “deslizou”.

# 5. Explain Core Concepts — Hard Ones Only

## 1. Reliability não aparece “de graça”

Este é provavelmente **o conceito mais importante da aula**.

Uma rede pode perder ou corromper informação.

Construímos fiabilidade adicionando mecanismos:

```text
CRC
+
ACK
+
timeout
+
retransmission
+
sequence numbers
```

Cada mecanismo resolve um problema diferente.

---

## 2. Timeout depende do contexto

Um timeout muito pequeno:

```text
mensagem apenas lenta
→ considerada perdida
→ retransmissão desnecessária
```

Muito grande:

```text
falha real
→ demora demasiado a ser detetada
```

Logo:

> timeout não é apenas “um número qualquer”.

Foi precisamente por isso que o professor insistiu bastante em **perceber o contexto e os números**.

---

## 3. Sequence number resolve ambiguidades

Sem sequence number:

```text
FRAME
FRAME
```

O receiver não sabe necessariamente se são:

```text
duas mensagens iguais
```

ou:

```text
uma mensagem + retransmissão
```

Com sequence number:

```text
FRAME #17
FRAME #17
```

fica possível reconhecer duplicação.

---

## 4. RTT explica porque Stop-and-Wait escala mal

Se:

```text
transmitir frame = 1 ms
RTT = 100 ms
```

o sender trabalha durante ~1 ms e depois fica grande parte do tempo à espera.

Sliding window permite utilizar esse tempo para transmitir outras frames.

---

## 5. Sliding Window junta performance + flow control

Não é apenas uma técnica para “ser mais rápido”.

Resolve dois problemas:

```text
não esperar constantemente → performance
não inundar o receiver      → flow control
```

Esse é o mental model que deves guardar.

# 6. Essential Exam Questions — 5 TOTAL

### 1 — Conceptual

**Qual é a principal diferença de fiabilidade entre UDP e TCP apresentada na aula?**

**Resposta:** UDP não fornece as mesmas garantias de entrega/ordenação; TCP fornece mecanismos de transmissão mais fiável e controlo de fluxo.

**Raciocínio:** com UDP, garantias adicionais podem ter de ser implementadas pela própria aplicação.

---

### 2 — Conceptual

**Qual é a diferença entre delay e jitter?**

**Resposta:** delay é o tempo de transmissão; jitter é a variação desse delay entre pacotes.

**Raciocínio:** 20 ms constantes podem ter baixo jitter, enquanto 5/50/10/80 ms apresentam jitter elevado.

---

### 3 — Practical

Um cliente UDP envia uma mensagem e espera indefinidamente por ACK. O ACK perde-se.

**Que problema ocorre e que mecanismo básico pode evitá-lo?**

**Resposta:** o cliente pode ficar bloqueado indefinidamente; deve existir um **timeout** seguido, se necessário, de retransmissão.

**Raciocínio:** UDP não garante que ACK ou mensagem cheguem.

---

### 4 — Practical

Depois de um timeout, o sender retransmite `Frame 5`, mas o receiver já tinha recebido `Frame 5`.

**Como pode reconhecer a duplicação?**

**Resposta:** usando **sequence numbers**.

**Raciocínio:** duas frames com o mesmo número podem ser identificadas como retransmissão/duplicado.

---

### 5 — Multiple Choice

Porque é usado Sliding Window?

A. Para eliminar endereços IP
B. Para transmitir várias frames antes de esperar todos os ACKs e controlar o fluxo
C. Para substituir CRC
D. Para transformar UDP em broadcast

**Resposta: B.**

**Raciocínio:** sliding window melhora utilização da ligação e limita a quantidade de dados pendentes no receiver.

# 7. Common Pitfalls

1. **Pensar que `send()` significa “chegou ao destino”.** Em UDP isso não é garantido.
2. **Confundir latency com jitter.** Latency = atraso; jitter = variação desse atraso.
3. **Pensar que TCP envia “um byte por pacote”.** TCP deve ser mentalizado como **byte stream**.
4. **Pensar que retransmitir resolve tudo.** Uma retransmissão pode criar duplicados; daí serem necessários **sequence numbers**.
5. **Pensar que Sliding Window serve apenas para velocidade.** Também é mecanismo de **flow control**, protegendo o recetor contra excesso de dados.

## 📓 Guardar no caderno

A relação mais importante desta aula é esta:

```text
Erro/corrupção ─────────────→ CRC
Mensagem perdida ───────────→ Timeout + retransmission
ACK perdido / duplicação ───→ Sequence number
RTT elevado ────────────────→ Sliding window
Receiver mais lento ────────→ Flow control
Requisitos diferentes ──────→ QoS
```

Se conseguires explicar **por que cada mecanismo existe**, já captaste o essencial desta primeira aula.
